# Design: 스토어 문구 반영 절차

## Context
로컬 자료 정리 범위와 대상 파일은 proposal.md를 따른다. 공개 버전에 대한 사용자 확인과 실제 대시보드 게시 확인은 별개 근거로 남긴다.

## Decisions
- RELEASE-002에 따라 게시 완료를 확인하기 전에는 실행하지 않는다. 사용자 확인을 취소하거나 현재 외부 상태를 임의로 단정하지 않는다.
- 같은 항목 ID `gmcaompgkpccmnpcbngeoabbfkgcoabg`의 실제 공개·검토 상태를 읽고, 대상 버전을 확인한 뒤 기존 문구와 로컬 후보를 비교한다. 새 코드 ZIP 업로드는 이 문구 작업에 포함하지 않는다.
- 개인정보 입력안은 권한·실제 데이터 처리와 대조한다. 심사 안내의 대시보드용 본문은 기존 운영 기록의 500자 한도에 맞추고 실제 화면 제한도 확인한다.
- 저장 성공, 필요한 검토 절차, 공개 문구 반영을 각각 확인하고 `store/submission.json`과 tasks에 관찰한 상태만 기록한다. 저장이 추가 심사를 요구하면 기존 공개본을 취소하거나 새 패키지를 올리지 않고 정확한 상태를 남긴다.

## Risks / Trade-offs
- 로컬과 공개 자료가 달라질 수 있음 → 실행 직전 비교하고 수정 범위를 필요한 문구로 제한한다.
- 자료 정리일이 게시일로 오인될 수 있음 → 근거와 날짜의 의미를 각각 기록한다.

## Migration Plan
게시 확인 → 현재 문구 비교 → 필요한 필드 저장 → 저장 내용 재확인 → 검토/공개 상태 기록 순서다. 원치 않는 문구 변경이 생기면 저장 전 확보한 기존 문구를 기준으로 복원하며 패키지를 교체하지 않는다.
