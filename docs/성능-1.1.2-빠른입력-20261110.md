# 1.1.2 빠른 드래그·단축키·작성 흐름의 성능 검토

2026-11-10 사용자 요청: 하단 미리보기가 지연을 유발하는지 확인하고, 빠르게 드래그해 단축키로 적용한 뒤 계속 작성하는 흐름에서 불필요한 지연을 검토한다.

결론: **하단 서식 미리보기 자체를 주요 병목으로 볼 근거는 없었다. 선택 처리의 전체 본문 재탐색, 패널 상태 갱신 대기, 서식 적용의 반복 읽기와 완료 대기가 우선 검토 대상이다.** 제품 코드를 수정하지 않은 조사 결과다.

## 측정 범위

- 기준: `/Users/msyu/study/geulbugi`, `main`, `3c80d75`, 소스/패키지 1.1.2.
- Ego Lite의 Chromium 156에서 별도 로컬 파일 진단 화면을 사용했다. 실제 네이버 원고·로그인 세션·설치 확장의 설정을 이번 성능 조사에서 변경하지 않았다.
- 현재 `EditorReader`/`NativeAdapter`/`App` 코드를 esbuild로 묶었다. React는 production 모드이며 실제 프로젝트 CSS를 사용한다.
- App 측정은 bridge/storage를 모의 처리해 네트워크·메시징·저장소 대기를 제외했다. 미리보기 제외 및 숨겨진 패널 제외 비교는 **생성된 진단 번들에서만** 수행했다.
- 서식 측정은 네이버 모양의 단순 문단과 버튼을 만들고, 버튼이 즉시 굵기를 반영하도록 모의 처리했다. 이는 네이버 실제 서버/편집기 처리 속도가 아니라 **글부기 자체 경로의 비용**을 분리하는 검사다.
- 밀리초 수치는 이 기기의 로컬 모형에서 관찰한 값이다. 실사이트 전체 입력 지연이나 모든 사용자의 지연 시간으로 일반화하지 않는다. UI 비교 시간은 동기 React render/commit을 측정하며 전체 paint/사용자 입력부터 화면 표시까지의 시간은 아니다.

## 1. 하단 서식 미리보기 자체의 영향은 작음

`src/ui/App.tsx:134`의 `.preset-preview`는 선택한 글의 앞 **80글자** 또는 예시 문장을 표시한다. 네트워크 요청·타이머·비동기 완료 대기는 없다. 일반 서식은 p 하나, 인용구는 QuotePreview 장식으로 렌더링한다.

400문단·저장 글 2,000개, 측정 전 워밍업 10회 후 선택 갱신 40회를 반복하고, 실행 순서를 바꾼 3라운드를 비교했다.

| 구성 | 라운드별 중앙값(ms) |
| --- | --- |
| 현재 UI | 1.2 / 1.0 / 0.8 |
| 하단 미리보기만 제외 | 1.2 / 1.2 / 0.8 |
| 숨겨진 내 글·예약 패널만 제외 | 1.1 / 1.4 / 0.6 |

미리보기 제외로 일관된 감소가 없었다. 숨겨진 패널 제외 역시 이 모형에서 큰 개선이 확정되지 않았다. 따라서 미리보기 삭제를 먼저 진행하기보다는 아래 입력/편집 경로를 개선하는 편이 타당하다. 미리보기를 숨겨도 그 데이터를 얻는 본문 읽기·선택 추적 경로는 그대로 남는다.

`내 글`과 `예약`은 hidden 상태로도 마운트된다(`App.tsx:137`, `150`). OwnPostsPanel은 표시되지 않아도 저장 글 필터/매핑을 수행한다. 불필요한 계산이므로 정리 후보지만, 이번 측정상 우선 병목은 아니다.

## 2. 같은 선택을 다시 알려도 전체 본문을 재탐색함

`EditorReader.captureSelection()` → `rememberRange()` → `read()`가 전체 문단·서식·사진 정보를 다시 읽고 document revision을 계산한다. `getComputedStyle`, DOM 탐색, 원문·서식의 직렬화/해시가 포함된다. `rememberRange()`는 선택이 이전과 같아도 `onChange()`를 호출한다.

글자 서식이 단순한 p/span 문단 모형의 결과:

| 본문 문단 수 | 전체 read 중앙값 | 선택 캡처 중앙값 | read 1회의 getComputedStyle 호출 |
| --- | --- | --- | --- |
| 20 | 0.4ms | 0.4ms | 120회 |
| 100 | 1.5ms | 1.6ms | 600회 |
| 400 | 6.2ms | 6.4ms | 2,400회 |

**선택을 바꾸지 않고 captureSelection을 15번 불러도 전체 읽기 15회·변경 알림 15회**가 발생했다. 실제 네이버 입력 버퍼 모형에서는 캡처마다 전체 읽기가 2회 발생했다.

실제 이벤트는 본문/네이티브 입력 iframe의 selectionchange·mouseup·keyup과 60ms 후 재캡처에서 들어온다. MutationObserver도 document.body 전체의 style/class/노드 변화를 감시한다. 따라서 단순히 화면 미리보기를 숨기는 것으로 선택 처리 비용이 없어지지 않는다.

개선 후보:

- 바뀌지 않은 선택과 반복 알림을 제거한다.
- 같은 시점의 본문 스냅샷을 선택 캡처/원문 검사에서 재사용한다.
- UI에는 가벼운 선택 상태를 전달하고, 본문 내용·서식 확인은 실제 변경 때 갱신한다.
- 본문이 실제 변경된 경우의 캐시 무효화와 단축키 실행 직전의 최신 선택 확인은 유지한다. 오래된 스냅샷으로 빠르게 처리하는 방식은 적절하지 않다.

## 3. 긴 문단의 커서 위치 추적 비용

`reader.ts:405` 이후 `nativeCaretRange()`는 네이버 공개 caret의 위치와 맞는 텍스트 경계를 찾기 위해 해당 문단의 **0부터 끝까지 각 문자 위치의 Range/getClientRects**를 검사한다. `captureBufferSelection()`의 collapsed 경로는 본문의 여러 후보 문단을 조사한다.

네이티브 입력 버퍼와 caret 모형을 만들고, 실제로 기대한 offset에 valid selection이 매핑되는 것을 확인한 뒤 7회 측정했다. 100문단 중 첫 문단의 길이만 바꿨다.

| 해당 문단 글자 수 | 캡처 중앙값 | p95 | 결과 |
| --- | --- | --- | --- |
| 60 | 4.0ms | 4.8ms | offset 30, valid |
| 600 | 5.5ms | 5.8ms | offset 300, valid |
| 3,000 | 16.1ms | 21.0ms | offset 1500, valid |

3,000글자 문단은 캡처 한 번만으로 약 한 프레임(60Hz 기준 16.7ms)에 해당하는 CPU 시간을 사용했다. 실제 한 입력에서 발생하는 이벤트 수와 네이버의 자체 비용은 이 수치에 포함하지 않았다.

개선 후보: 마지막으로 확인한 문단/시각적 줄/근처 offset부터 검사하고, 일치하지 않을 때 전체 탐색으로 폴백한다. 단순 이진 탐색은 줄바꿈·양방향 문자·동일 좌표 등 때문에 안전성이 보장되지 않으므로 현재 모호한 위치 거부 정책을 유지해야 한다.

## 4. 패널 선택 표시는 마지막 알림 뒤 500ms 대기

`src/ui/App.tsx:70`은 PANEL_REFRESH를 받을 때마다 기존 타이머를 취소하고 500ms 뒤에 스냅샷을 읽는다. 알림이 계속 들어오면 이 대기가 계속 밀린다. 별도로 5초마다 poll한다(`App.tsx:78`).

실제 App + fake timer 검사 2개를 추가했다.

1. 100ms 간격으로 20번 알림을 보내면 그동안 새 조회가 없고, 마지막 알림 뒤 500ms가 되어야 조회했다.
2. 100ms 간격 알림을 4.9초 지속하면 새 조회가 없고, 5초 주기 poll 때 조회했다.

이 때문에 본문 선택이 바뀌었는데 패널의 선택 안내/적용 가능 상태/미리보기가 늦게 따라올 수 있다. **이 500ms는 단축키 실행 자체에 붙는 대기가 아니다.** 단축키는 background의 command 핸들러에서 편집기로 직접 전달되며 미리보기 갱신 완료를 기다리지 않는다.

개선 후보: 선택 표시 갱신과 본문/연결 상태 재조회 경로를 분리한다. 입력 알림마다 전체 본문을 즉시 읽게 바꾸면 CPU 부담이 커지므로, 500ms 숫자만 낮추는 수정으로 끝내지 않는다.

## 5. 서식마다 안정화 대기 + 마지막 고정 대기가 누적됨

- `PublicEditorUI.clickEdit()`는 각 실제 서식 변경 후 `waitNativeRevision()`을 호출한다.
- `native-operation.ts:13`은 revision이 바뀐 뒤 **80ms 안정 상태**를 기다리며 40ms 간격으로 검사한다.
- `NativeAdapter.handle()`은 서식 작업 묶음 뒤에도 **100ms를 항상 기다린다**(`native-adapter.ts:272`).
- 검사 루프의 guard와 current read가 각각 전체 본문을 읽고, chosenBlocks/chosenRuns/최종 검증 등에서도 반복 읽기가 추가된다.

미리보기도 패널도 없는 편집 모형에서 굵게 1회 결과:

| 문단 수 | 전체 소요 | 전체 read 호출 |
| --- | --- | --- |
| 20 | 200.4ms | 20회 |
| 100 | 225.3ms | 20회 |
| 400 | 317.3ms | 20회 |

여러 속성을 실제로 바꾸는 프리셋은 해당 도구들을 순서대로 처리하므로 대기가 누적된다. 이미 같은 값이면 도구 실행을 건너뛰는 최적화는 현재도 존재한다.

100문단 모형에서 다음 요청을 첫 요청 후 **40ms 또는 120ms**에 보내면 모두 `진행 중인 작업이 끝날 때까지 기다려 주세요.`로 거절됐다. 첫 요청은 약 222~224ms에 성공했다. 현재는 다음 서식 요청을 큐에 보관하는 기능이 없다. 이는 단순 성능뿐 아니라 빠른 연속 조작의 처리 정책 문제다.

실제 키 입력은 진행 중인 서식의 직접 편집 보호에도 걸린다. 특히 현재 코드는 마지막 고정 대기 중에도 guard를 유지하므로, 서식이 화면에 보이자마자 입력하는 사용자는 완료 전 입력으로 판정될 여지가 있다. 이 조건은 소스 검토이며, 이번 로컬 모형으로 네이버 실제 사용자 입력 타이밍까지 재현한 것은 아니다.

개선 후보:

- guard와 revision 검사에 같은 읽기 결과를 공유해 반복 전체 탐색을 줄인다.
- 각 속성이 기대 상태가 됐는지 확인하는 절차와 작업 묶음의 최종 안정화 확인을 정리해 중복 대기를 줄인다.
- 마지막 100ms 고정 대기는 실제 완료 조건 기반 검증으로 대체할 수 있는지 먼저 실환경에서 확인한다.
- 무조건 대기를 없애거나 미완료 요청을 그대로 큐에 넣지 않는다. 다음 요청에 사용자가 선택한 범위·탭·세션이 달라질 수 있으므로 대상 보존·실패·직접 입력 정책을 명세해야 한다.

## 6. 단축키의 전체 DB 읽기·검증도 부가 비용

`background.ts:117`은 매 단축키마다 loadDatabase를 호출한다. loadDatabase는 저장한 모든 게시글까지 hydrate/validate한다. 이 과정은 미리보기와 별개로 명령 전달 전에 실행된다.

이번 이전 검수 환경에는 저장 글이 0개였으므로 그 환경의 주된 원인으로 단정하지 않는다. 글 자료가 많은 설치본에서는 IPC/복사/검증 비용이 증가할 수 있다. 현재 PANEL-001은 매 실행 시 최신 저장 슬롯을 읽도록 요구하므로, 설정 변경을 놓치는 단순 영구 캐시 대신 별도 설정 읽기 또는 변경 통지를 반영하는 검증된 캐시를 검토해야 한다. 이 항목은 소스 검토이며 별도 저장소 실측을 하지 않았다.

## 권장 우선순위

1. 이전 조사에서 찾은 지연 응답의 세션/순서 역전을 함께 해결한다. 빠르게 처리해도 잘못된 상태를 표시하면 연속 작업을 신뢰할 수 없다.
2. 선택 추적의 중복 전체 읽기와 긴 문단 caret 탐색을 줄인다.
3. 선택 표시와 무거운 본문 조회를 분리한다.
4. 원문·선택 밖 서식·사진·undo 검증을 유지하며 서식의 반복 읽기/중복 대기를 줄인다.
5. 단축키 설정 읽기와 숨겨진 패널 계산을 정리한다. 하단 미리보기 삭제는 우선순위가 낮다.

아직 구현·커밋·푸시·빌드 재생성을 수행하지 않았다. 빠른 연속 적용의 정책을 포함한 구현은 별도 OpenSpec change에서 다뤄야 한다.
